\subsection{Query 72 Optimization: Resolving Fact-to-Fact Join Explosion}

\subsubsection{Baseline Query Analysis and Bottlenecks}
In our baseline Power Test across Scale Factors 1, 2, 4, and 8, \textbf{Query 72} was the single largest performance bottleneck in the entire 99-query workload, requiring \textbf{110.44s} at SF1 and degrading by $48.93\times$ to \textbf{5,404.38s (1.5 hours)} at SF8. 

Listing~\ref{lst:q72_orig} shows the baseline query from \texttt{qmod\_combined/query72.sql}.

\begin{lstlisting}[language=SQL, caption={Baseline Query 72 (\texttt{qmod\_combined/query72.sql})}, label={lst:q72_orig}, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
SELECT i_item_desc
      ,w_warehouse_name
      ,d1.d_week_seq
      ,SUM(CASE WHEN p_promo_sk IS NULL THEN 1 ELSE 0 END) no_promo
      ,SUM(CASE WHEN p_promo_sk IS NOT NULL THEN 1 ELSE 0 END) promo
      ,COUNT(*) total_cnt
FROM catalog_sales
JOIN inventory ON (cs_item_sk = inv_item_sk AND inv_quantity_on_hand < cs_quantity)
JOIN warehouse ON (w_warehouse_sk = inv_warehouse_sk)
JOIN item ON (i_item_sk = cs_item_sk)
JOIN date_dim d1 ON (cs_sold_date_sk = d1.d_date_sk)
JOIN date_dim d2 ON (inv_date_sk = d2.d_date_sk AND d1.d_week_seq = d2.d_week_seq)
JOIN date_dim d3 ON (cs_ship_date_sk = d3.d_date_sk AND d3.d_date > d1.d_date + 5)
LEFT OUTER JOIN promotion ON (cs_promo_sk = p_promo_sk)
WHERE d1.d_year = 2002
  AND EXISTS (SELECT 1 FROM household_demographics JOIN catalog_sales ON cs_bill_hdemo_sk = hd_demo_sk WHERE hd_buy_potential = '>10000' LIMIT 1)
  AND EXISTS (SELECT 1 FROM customer_demographics JOIN catalog_sales ON cs_bill_cdemo_sk = cd_demo_sk WHERE cd_marital_status = 'U' LIMIT 1)
GROUP BY i_item_desc, w_warehouse_name, d1.d_week_seq
ORDER BY total_cnt DESC, i_item_desc, w_warehouse_name, d_week_seq
LIMIT 100;
\end{lstlisting}

An inspection of the relational structure reveals three compounding bottlenecks in MySQL:
\begin{enumerate}
    \item \textbf{Unfiltered Fact-to-Fact Join Explosion:} \texttt{inventory} is the largest fact table in the TPC-DS schema ($\approx 11.7\text{M}$ rows at SF1; $\approx 94\text{M}$ rows at SF8), and \texttt{catalog\_sales} contains $\approx 1.44\text{M}$ rows at SF1 ($\approx 11.5\text{M}$ rows at SF8). Joining \texttt{catalog\_sales} directly to \texttt{inventory} on \texttt{cs\_item\_sk = inv\_item\_sk} before restricting both tables to the target weeks of 2002 causes MySQL to probe inventory snapshots across all years, only to discard large amounts of the intermediate pairs when \texttt{date\_dim d2} (\texttt{d1.d\_week\_seq = d2.d\_week\_seq}) and \texttt{date\_dim d3} (\texttt{d3.d\_date > d1.d\_date + 5}) are evaluated later.
    \item \textbf{Uncorrelated \texttt{EXISTS} Subqueries:} The previous modification replaced the demographic joins with two \texttt{EXISTS (... LIMIT 1)} subqueries that re-declare \texttt{catalog\_sales} internally without correlation to the outer query. While they evaluate to constant \texttt{TRUE}, MySQL still materializes and deduplicates these subqueries if not properly isolated.
    \item \textbf{Late Aggregation Over Wide Strings:} Joining \texttt{item} (\texttt{i\_item\_desc}, \texttt{VARCHAR(200)}) and \texttt{warehouse} (\texttt{w\_warehouse\_name}) prior to aggregation forces MySQL's temporary aggregation table to hash wide string keys over millions of unaggregated join pairs.
\end{enumerate}

\subsubsection{First Improvement Attempt: Predicate Pushdown via CTEs}
Our first optimization attempt (Iteration 1) restructured the query using Common Table Expressions (CTEs) to push down the 2002 date filters (\texttt{d1\_2002} and \texttt{d2\_2002}) into \texttt{catalog\_sales} (\texttt{filtered\_cs}) and \texttt{inventory} (\texttt{filtered\_inv}) prior to the fact-to-fact join, as shown in Listing~\ref{lst:q72_v1}.

\begin{lstlisting}[language=SQL, caption={First Optimization Attempt (Iteration 1: CTE Predicate Pushdown)}, label={lst:q72_v1}, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH d1_2002 AS (
    SELECT d_date_sk, d_week_seq, d_date
    FROM date_dim WHERE d_year = 2002
),
d2_2002 AS (
    SELECT d2.d_date_sk, d2.d_week_seq
    FROM date_dim d2
    WHERE d2.d_week_seq IN (SELECT DISTINCT d_week_seq FROM d1_2002)
),
filtered_cs AS (
    SELECT cs.cs_item_sk, cs.cs_quantity, cs.cs_promo_sk, d1.d_week_seq
    FROM catalog_sales cs
    STRAIGHT_JOIN d1_2002 d1 ON cs.cs_sold_date_sk = d1.d_date_sk
    STRAIGHT_JOIN date_dim d3 ON cs.cs_ship_date_sk = d3.d_date_sk
     AND d3.d_date > d1.d_date + 5
),
filtered_inv AS (
    SELECT inv.inv_item_sk, inv.inv_warehouse_sk, inv.inv_quantity_on_hand, d2.d_week_seq
    FROM d2_2002 d2
    STRAIGHT_JOIN inventory inv ON inv.inv_date_sk = d2.d_date_sk
)
SELECT i.i_item_desc, w.w_warehouse_name, cs.d_week_seq,
       SUM(CASE WHEN p.p_promo_sk IS NULL THEN 1 ELSE 0 END) AS no_promo,
       SUM(CASE WHEN p.p_promo_sk IS NOT NULL THEN 1 ELSE 0 END) AS promo,
       COUNT(*) AS total_cnt
FROM filtered_cs cs
JOIN filtered_inv inv
  ON cs.cs_item_sk = inv.inv_item_sk
 AND cs.d_week_seq = inv.d_week_seq
 AND inv.inv_quantity_on_hand < cs.cs_quantity
JOIN warehouse w ON w.w_warehouse_sk = inv.inv_warehouse_sk
JOIN item i ON i.i_item_sk = cs.cs_item_sk
LEFT OUTER JOIN promotion p ON cs.cs_promo_sk = p.p_promo_sk
WHERE EXISTS (SELECT 1 FROM household_demographics JOIN catalog_sales ON cs_bill_hdemo_sk = hd_demo_sk WHERE hd_buy_potential = '>10000' LIMIT 1)
  AND EXISTS (SELECT 1 FROM customer_demographics JOIN catalog_sales ON cs_bill_cdemo_sk = cd_demo_sk WHERE cd_marital_status = 'U' LIMIT 1)
GROUP BY i_item_desc, w.w_warehouse_name, cs.d_week_seq
ORDER BY total_cnt DESC, i_item_desc, w.w_warehouse_name, cs.d_week_seq
LIMIT 100;
\end{lstlisting}

\subsubsection{Why Iteration 1 Failed at SF8: \texttt{EXPLAIN FORMAT=TREE} Analysis}
On SF1, SF2, and SF4, Iteration 1 achieved substantial speedups, reducing execution time from \textbf{110.44s to 43.96s} ($2.51\times$) on SF1, \textbf{698.31s to 122.45s} ($5.70\times$) on SF2, and \textbf{1,676.24s to 352.00s} ($4.76\times$) on SF4. However, when executed on \textbf{SF8 (\texttt{tpcds8})}, the query stalled, approaching its original execution time (5404.38s). We decided to manually terminate the query execution and inspect what went wrong.

To diagnose why the scaling curve broke at SF8, we inspected MySQL's execution plan on \texttt{tpcds8} using \texttt{EXPLAIN FORMAT=TREE} (Listing~\ref{lst:q72_explain_bad}).

The \texttt{EXPLAIN FORMAT=TREE} output exposes two critical flaws in Iteration 1:
\begin{enumerate}
    \item \textbf{Optimizer \texttt{derived\_merge} Unmerged the CTE Boundary:} Because MySQL's \texttt{derived\_merge} optimization is enabled by default, the optimizer dissolved \texttt{filtered\_cs} and \texttt{filtered\_inv} back into the global join graph. It then initiated the plan with a Cartesian hash join between \texttt{warehouse w} and \texttt{date\_dim d2} (\texttt{rows=420e+6}), probed \texttt{inventory} (\texttt{rows=79.3e+6}), and performed an unindexed nested-loop lookup into \texttt{catalog\_sales} by \texttt{cs\_item\_sk} alone, generating \textbf{2.17 billion intermediate rows} (\texttt{cost=42.6e+9 rows=2.17e+9}) before ever checking whether \texttt{cs\_sold\_date\_sk} was in 2002.
    \item \textbf{Full Table Scan in \texttt{filtered\_cs}:} Inside \texttt{filtered\_cs}, writing \texttt{FROM catalog\_sales cs STRAIGHT\_JOIN d1\_2002 d1} forced a full table scan of all 11.5M rows of \texttt{catalog\_sales} at SF8 instead of driving from the 365 rows of \texttt{d1\_2002} into the foreign-key index \texttt{cs\_d2 (cs\_sold\_date\_sk)}.
\end{enumerate}

\subsubsection{Second Improvement (Final): Pre-Aggregated Materialized CTEs \& Composite PK Lookup}
To eliminate the 2.17-billion-row nested loop on SF8 while preserving 100\% exact semantic equivalence, we applied three relational and physical optimizations (Listing~\ref{lst:q72_v2}):
\begin{enumerate}
    \item \textbf{Early Aggregation of \texttt{catalog\_sales} (Distributive Aggregate Pushdown):} 
    By the distributive property of aggregation over join, any two \texttt{catalog\_sales} rows in the same week that share the same $(\texttt{cs\_item\_sk}, \texttt{d\_week\_seq}, \texttt{cs\_quantity})$ match the exact same set of \texttt{inventory} records under the join predicate $(\texttt{cs\_item\_sk} = \texttt{inv\_item\_sk} \land \texttt{d1.d\_week\_seq} = \texttt{d2.d\_week\_seq} \land \texttt{inv\_quantity\_on\_hand} < \texttt{cs\_quantity})$. Formally:
    \[\gamma_{G,\, \text{SUM}(p),\, \text{COUNT}(*)}\left(\text{CS} \bowtie_{\theta} \text{INV}\right) \equiv \gamma_{G,\, \text{SUM}(\text{cnt}_p),\, \text{SUM}(\text{cnt}_{*})}\left( \left(\gamma_{\text{cs\_item\_sk},\, \text{d\_week\_seq},\, \text{cs\_quantity},\, \text{SUM}(p)\to\text{cnt}_p,\, \text{COUNT}(*)\to\text{cnt}_{*}}(\text{CS})\right) \bowtie_{\theta} \text{INV} \right)\]
    Pre-grouping \texttt{filtered\_cs} by $(\texttt{cs\_item\_sk}, \texttt{d1.d\_week\_seq}, \texttt{cs\_quantity})$ both forces CTE materialization and collapses duplicate item-week-quantity sales before probing \texttt{inventory}.
    \item \textbf{Index-Driven Join Order (\texttt{d1\_2002} $\to$ \texttt{catalog\_sales}):} Driving \texttt{filtered\_cs} from \texttt{d1\_2002} via \texttt{STRAIGHT\_JOIN catalog\_sales cs} utilizes the foreign-key index \texttt{cs\_d2 (cs\_sold\_date\_sk)} to read only 2002 sales.
    \item \textbf{Exploiting \texttt{inventory}'s Composite Primary Key:} In TPC-DS, the primary key of \texttt{inventory} is \texttt{PRIMARY KEY (inv\_date\_sk, inv\_item\_sk, inv\_warehouse\_sk)}. Once \texttt{filtered\_cs} is materialized and joined to \texttt{d2\_2002} on \texttt{d\_week\_seq} (7 \texttt{d\_date\_sk} values per week), MySQL performs a direct 2-column composite Primary Key lookup into \texttt{inventory} on \texttt{(inv\_date\_sk = d2.d\_date\_sk, inv\_item\_sk = cs.cs\_item\_sk)}, completely avoiding scanning the 94M-row \texttt{inventory} table.
\end{enumerate}

\begin{lstlisting}[language=SQL, caption={Final Optimized Query 72 (Pre-Aggregated Materialized CTEs \& Composite PK Lookup)}, label={lst:q72_v2}, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH /*+ SET_VAR(join_buffer_size=1073741824) SET_VAR(tmp_table_size=1073741824) SET_VAR(max_heap_table_size=1073741824) */
d1_2002 AS (
    SELECT /*+ NO_MERGE() */ d_date_sk, d_week_seq, d_date
    FROM date_dim
    WHERE d_year = 2002
),
d2_2002 AS (
    SELECT /*+ NO_MERGE() */ d2.d_date_sk, d2.d_week_seq
    FROM date_dim d2
    WHERE d2.d_week_seq IN (SELECT DISTINCT d_week_seq FROM d1_2002)
),
filtered_cs AS (
    SELECT /*+ NO_MERGE() */
           cs.cs_item_sk,
           d1.d_week_seq,
           cs.cs_quantity,
           SUM(CASE WHEN p.p_promo_sk IS NULL THEN 1 ELSE 0 END) AS no_promo_cnt,
           SUM(CASE WHEN p.p_promo_sk IS NOT NULL THEN 1 ELSE 0 END) AS promo_cnt,
           COUNT(*) AS cs_cnt
    FROM d1_2002 d1
    STRAIGHT_JOIN catalog_sales cs
      ON cs.cs_sold_date_sk = d1.d_date_sk
    STRAIGHT_JOIN date_dim d3
      ON cs.cs_ship_date_sk = d3.d_date_sk
     AND d3.d_date > d1.d_date + 5
    LEFT OUTER JOIN promotion p
      ON cs.cs_promo_sk = p.p_promo_sk
    GROUP BY cs.cs_item_sk, d1.d_week_seq, cs.cs_quantity
),
filtered_inv AS (
    SELECT /*+ NO_MERGE() */
           inv.inv_item_sk,
           inv.inv_warehouse_sk,
           d2.d_week_seq,
           inv.inv_quantity_on_hand
    FROM d2_2002 d2
    STRAIGHT_JOIN inventory inv
      ON inv.inv_date_sk = d2.d_date_sk
)
SELECT /*+ BNL(cs, inv) */
       i.i_item_desc,
       w.w_warehouse_name,
       cs.d_week_seq,
       SUM(cs.no_promo_cnt) AS no_promo,
       SUM(cs.promo_cnt) AS promo,
       CAST(SUM(cs.cs_cnt) AS SIGNED) AS total_cnt
FROM filtered_cs cs
STRAIGHT_JOIN filtered_inv inv
  ON cs.cs_item_sk = inv.inv_item_sk
 AND cs.d_week_seq = inv.d_week_seq
 AND inv.inv_quantity_on_hand < cs.cs_quantity
STRAIGHT_JOIN warehouse w
  ON w.w_warehouse_sk = inv.inv_warehouse_sk
STRAIGHT_JOIN item i
  ON i.i_item_sk = cs.cs_item_sk
WHERE EXISTS (
    SELECT 1 FROM household_demographics
    JOIN catalog_sales ON cs_bill_hdemo_sk = hd_demo_sk
    WHERE hd_buy_potential = '>10000' LIMIT 1
)
AND EXISTS (
    SELECT 1 FROM customer_demographics
    JOIN catalog_sales ON cs_bill_cdemo_sk = cd_demo_sk
    WHERE cd_marital_status = 'U' LIMIT 1
)
GROUP BY i.i_item_desc, w.w_warehouse_name, cs.d_week_seq
ORDER BY total_cnt DESC, i.i_item_desc, w.w_warehouse_name, cs.d_week_seq
LIMIT 100;
\end{lstlisting}

Listing~\ref{lst:q72_explain_good} shows the resulting \texttt{EXPLAIN FORMAT=TREE} plan on SF8, confirming that \texttt{filtered\_cs} is materialized via index \texttt{cs\_d2} and that \texttt{inventory} is accessed via a direct two-column primary key lookup (\texttt{inv\_date\_sk = d2.d\_date\_sk, inv\_item\_sk = cs.cs\_item\_sk}, \texttt{rows=8.08}).
