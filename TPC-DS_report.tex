\chapter{Background}

\section{Project Overview}

This report presents Part I of the course data-warehouse project: implementing and evaluating the TPC-DS decision-support benchmark on MySQL 8.0. We run the benchmark at scale factors 1, 2, 4, and 8 to study how query performance changes as the dataset grows. Our objectives are to identify bottlenecks in MySQL's execution of analytical queries and to evaluate query-rewriting and execution-plan strategies for improving runtimes. The scope of this report is the TPC-DS workload and its performance on MySQL.

\section{TPC-DS}

TPC-DS (Transaction Processing Performance Council Decision Support) is the industry standard for evaluating decision support systems (DSS) and Big Data engines. Unlike synthetic benchmarks that test isolated database primitives, TPC-DS models the holistic analytical operations of a multi-channel retail business (Store, Web, and Catalog sales).

\subsubsection{The Multi-Channel Star Schema and Snowflaking}

The TPC-DS schema consists of 24 tables arranged primarily as a set of interconnected Star Schemas and selective Snowflake Schemas:

\begin{itemize}
    \item \textbf{Fact Tables (7):}
        \begin{itemize}
            \item store\_sales, store\_returns
            \item catalog\_sales, catalog\_returns
            \item web\_sales, web\_returns
            \item inventory (snapshot fact table)
        \end{itemize}
    \item \textbf{Dimension Tables (17):}
        \begin{itemize}
            \item \textbf{Core Shared Dimensions:} date\_dim, time\_dim, item, customer, customer\_address, promotion, warehouse.
            \item \textbf{Demographic Dimensions:} customer\_demographics, household\_demographics, income\_band.
            \item \textbf{Channel Dimensions:} store, web\_site, web\_page, call\_center, catalog\_page.
        \end{itemize}
\end{itemize}

\subsubsection{Data Characteristics and Complexity}

\begin{itemize}
    \item \textbf{Data Skew:} Real-world retail datasets exhibit non-uniform distributions (e.g., peak sales on weekends/holidays, high-frequency buyers vs. one-time customers). TPC-DS incorporates data skew across foreign keys, which tests how database query optimizers handle non-linear selectivity.
    \item \textbf{Slowly Changing Dimensions:} Dimensions like item and customer maintain historical versions across time using effective date ranges, forcing queries to join on both surrogate keys and date ranges.
    \item \textbf{Data Maintenance Operations:} In addition to read-only queries, TPC-DS benchmarks data maintenance via concurrent refresh streams:
    \begin{itemize}
        \item \textbf{Insert Stream:} Ingesting new staging data (s\_store\_sales, etc.).
        \item \textbf{Delete Stream:} Removing expired date ranges from core fact tables based on surrogate key lookups (ss\_sold\_date\_sk).
    \end{itemize}
\end{itemize}


\section{MySQL}

MySQL is a widely adopted relational database management system built around the ACID-compliant InnoDB storage engine. Traditionally engineered for Online Transaction Processing (OLTP) environments, MySQL relies on a cost-based optimizer (CBO) to evaluate execution paths for complex SQL statements. When applied to decision support workloads like TPC-DS, MySQL processes complex multi-table joins, subqueries, and advanced analytical features such as window functions and aggregate windowing operations introduced in modern SQL standards. Its foundational architecture utilizes row-level locking, clustered B-tree index structures, and Write-Ahead Logging (WAL) to maintain transactional integrity while executing multi-channel analytical queries.

\section{Generalised Relational and Physical Optimization Framework}

Across the 99-query TPC-DS workload at Scale Factors (SF) 1, 2, 4, and 8, some queries exhibited runtime increases of approximately $50\times$ to more than $1{,}900\times$ between SF4 and SF8. These observations motivate a framework for analysing recurring sources of work in analytical queries, rather than treating each slow query as an isolated case. The framework comprises three complementary optimisation laws: reduce data through early aggregation, eliminate unnecessary rows through early filtering, and arrange the remaining joins and accesses appropriately. Each law is grounded in relational equivalences, but its physical benefit depends on query semantics, data distribution, indexes, and the execution plan selected by MySQL.

\subsection{Law I: Distributive Aggregate Pushdown (Early Surrogate-Key Grouping)}

\subsubsection{Theoretical Foundation}
Let $R$ be a fact relation with join key $k$ and measure $x$, and let $S$ be a dimension relation whose key $k$ uniquely identifies each dimension row. If the final grouping attribute $g$ is determined by that key, then a distributive aggregate such as \texttt{SUM} may be computed over $R$ before the join:
\begin{equation}
\gamma_{g;\,\text{SUM}(x)}(R \bowtie_{R.k=S.k} S)
\;\equiv\;
\gamma_{g;\,\text{SUM}(\text{partial\_sum})}
\left(
\gamma_{k;\,\text{SUM}(x)\to\text{partial\_sum}}(R)
\bowtie_{R.k=S.k} S
\right)
\end{equation}
In practice, the early grouping key must also retain every fact-side attribute required by the final groups, joins, and predicates. Grouping by a surrogate key is lossless with respect to a dimension description only when the join key identifies the relevant dimension row; where multiple keys map to the same output description, a final aggregation by that description is still required. For \texttt{AVG}, the partial state must include both sum and count; averaging partial averages is generally incorrect. Likewise, partial \texttt{COUNT(DISTINCT)} values cannot in general be summed when their underlying values overlap.

\paragraph{Illustrative SQL.}
The following query first combines store sales by date key, then joins the reduced result to \texttt{date\_dim} to report annual totals:
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH sales_by_date AS (
    SELECT ss_sold_date_sk, SUM(ss_sales_price) AS partial_sales
    FROM store_sales
    GROUP BY ss_sold_date_sk
)
SELECT d.d_year, SUM(s.partial_sales) AS annual_sales
FROM sales_by_date AS s
JOIN date_dim AS d
    ON d.d_date_sk = s.ss_sold_date_sk
GROUP BY d.d_year;
\end{lstlisting}
This rewrite assumes that \texttt{d\_date\_sk} uniquely identifies a date row and retains the original inner-join semantics. A query with additional fact-side grouping attributes or filters must preserve them at the appropriate stage.

\subsubsection{Physical Impact in MySQL}
Joining fact rows to dimensions before grouping can make the grouping input large and require wide descriptive values to be carried through intermediate processing. Early aggregation can reduce both the row count and row width before the dimension join, particularly when many fact rows share a relatively small set of keys. MySQL may use internal temporary tables or sorting during grouping; depending on the plan, intermediate size, and server settings, temporary data may also be written to disk. These outcomes are plan-dependent: aggregation is beneficial only when the reduced intermediate result and its processing cost outweigh the work of the rewrite.

\subsection{Law II: Selection Pushdown and Disjunctive (\texttt{OR}) Bounding-Box Extraction}

\subsubsection{Theoretical Foundation}
For an inner join, a predicate that refers only to one input can be applied to that input before the join:
\begin{equation}
\sigma_{p(R)}(R \bowtie_{\theta} S)
\;\equiv\;
\sigma_{p(R)}(R) \bowtie_{\theta} S
\end{equation}
When an \texttt{OR} condition couples predicates from both relations, define $p_i(R)$ and $q_i(S)$ as the table-local predicates in branch $i$. The original condition can be retained as a residual predicate after applying necessary, potentially broader filters to each input:
\begin{equation}
\sigma_{\bigvee_{i=1}^{k}(p_i(R)\land q_i(S))}
(R \bowtie_{\theta} S)
\;\equiv\;
\sigma_{\bigvee_{i=1}^{k}(p_i(R)\land q_i(S))}
\left(
\sigma_{\bigvee_{i=1}^{k}p_i(R)}(R)
\bowtie_{\theta}
\sigma_{\bigvee_{i=1}^{k}q_i(S)}(S)
\right)
\end{equation}
The per-relation disjunctions form a candidate superset, not an exact replacement for the original branch pairings: rows satisfying predicates from different branches may pass the prefilters. Retaining the full residual condition removes those false positives. The same principle permits an outer restriction, such as a target year, to be propagated into a CTE that scans a fact table, provided the transformation preserves the original semantics.

\paragraph{Illustrative SQL.}
Here the date and sales CTEs restrict each relation to values that occur in at least one branch. The \texttt{WHERE} clause then preserves the original branch-by-branch condition:
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH candidate_dates AS (
    SELECT d_date_sk, d_year
    FROM date_dim
    WHERE d_year IN (2001, 2002)
),
candidate_sales AS (
    SELECT ss_sold_date_sk, ss_sales_price, ss_quantity
    FROM store_sales
    WHERE ss_sales_price > 100 OR ss_quantity >= 10
)
SELECT d.d_year, COUNT(*) AS qualifying_sales
FROM candidate_sales AS s
JOIN candidate_dates AS d
    ON d.d_date_sk = s.ss_sold_date_sk
WHERE (d.d_year = 2001 AND s.ss_sales_price > 100)
   OR (d.d_year = 2002 AND s.ss_quantity >= 10)
GROUP BY d.d_year;
\end{lstlisting}
The CTE predicates are only safe because they retain every branch of the original condition; the final \texttt{WHERE} expression must not be weakened or omitted.

\subsubsection{Physical Impact in MySQL}
Cross-table disjunctions can make it difficult for an optimiser to identify selective access paths or apply every table-local condition before joining. Explicit candidate filters may reduce rows entering the join, while the residual predicate preserves the original logic; whether MySQL uses those filters early or chooses index access must be verified in the execution plan. In our Query 13 measurements, the SF8 baseline runtime was 715.51\,s, but the SF8 execution trees were not collected. This timing therefore documents the observed scaling problem, not a particular physical cause. The available SF1 baseline tree shows a scan of 50,000 \texttt{customer\_address} rows followed by 13,837 address-driven lookups into \texttt{store\_sales}, with the 2001 date condition applied later in the join sequence.

\subsection{Law III: Join Associativity, CTE Materialisation (\texttt{NO\_MERGE}), and Composite PK/FK Driving Order}

\subsubsection{Theoretical Foundation}
For inner joins with the same join predicates, associativity permits alternative join trees:
\begin{equation}
(R \bowtie_{\theta_1} S) \bowtie_{\theta_2} T
\;\equiv\;
R \bowtie_{\theta_1} (S \bowtie_{\theta_2} T)
\end{equation}
Here, $\theta_1$ and $\theta_2$ denote the same join predicates in both trees. Although these equivalent join trees return the same relational result, they may produce different intermediate cardinalities and access costs. Applying a selective dimension restriction before joining large fact relations can be advantageous when it reduces the input substantially. The equivalence does not extend indiscriminately across outer joins or other operators whose semantics depend on evaluation order.

\paragraph{Illustrative SQL.}
The example filters the date dimension before joining it to store sales. The hint discourages merging the eligible CTE, while \texttt{STRAIGHT\_JOIN} expresses the intended left-to-right join order:
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH filtered_dates AS (
    SELECT d_date_sk
    FROM date_dim
    WHERE d_year = 2001
)
SELECT /*+ NO_MERGE(filtered_dates) */
       COUNT(*) AS sale_rows
FROM filtered_dates AS d
STRAIGHT_JOIN store_sales AS s
    ON s.ss_sold_date_sk = d.d_date_sk;
\end{lstlisting}
The hint and join construct shape aspects of planning; they do not guarantee that a particular index will be used or that the resulting plan will be faster.

\subsubsection{Physical Impact in MySQL}
MySQL's cost-based optimiser estimates row counts and costs when selecting join orders and access paths. Two mechanisms can be considered when those choices are demonstrably poor:
\begin{enumerate}
    \item \textbf{CTE and derived-table materialisation:} MySQL may merge an eligible query block into its outer query or materialise it as an intermediate result. The \texttt{NO\_MERGE} hint can discourage merging for eligible CTEs or derived tables, which may be useful when a selective result should remain a separate input. Materialisation also incurs computation and storage costs, and the hint does not prescribe the outer join order.
    \item \textbf{Join-order and index access:} \texttt{STRAIGHT\_JOIN} constrains join order and can make a small filtered relation the intended driving input. In InnoDB, rows are organized by the clustered primary key, while secondary indexes provide additional access paths. A suitable index whose leading columns match the join predicates can support selective lookups into a fact table; a foreign-key constraint alone does not guarantee that every desired access path is efficient. Index lookups may be less attractive when they retrieve a large fraction of the table.
\end{enumerate}
Accordingly, materialisation, join-order control, and index selection should be evaluated together using \texttt{EXPLAIN} or \texttt{EXPLAIN ANALYZE} and measurements at the relevant scale factors. Statistics, selectivity, intermediate-result size, and index definitions can change which plan is preferable.

\chapter{Implementation}

\section{System Requirements}
All benchmarks were run on a MacBook Pro with an Apple M5 Pro chip and 24GB of unified memory, connected to AC power with High Power Mode enabled and disk/system sleep disabled. To maximise in-memory output without triggering OS memory pressure, we allocated 14GB of RAM to the MySQL InnoDB Buffer Pool, an extra 1GB for in-memory temporary tables and 256MB per hash-join buffer and 64MB per sort buffer. This setup leaves enough room for OS system processes, ensuring no buffer pool pages are swapped to SSD.

\section{Methodology}
\label{sec:methodology}
Following standard scientific principles in TPC-DS (CITE), we execute each query 5 times across each scalefactor (SF1, SF2, SF4, SF8). To isolate steady-state warm cache performance from cold-disk I/O, we treat Run 1 as a cache warmup run, and compute the mean, median and standard deviation across Runs 2 to 5. Between scale factors, MySQL is restarted to flush the InnoDB Buffer Pool. As our baseline, we used the queries from STUDENT REF repository.

\section{Important Notice}
\label{sec:important_notice}
During our work, we noticed that some of the baseline rewrites introduced by STUDENT REF altered the original query semantics.

The following 4 queries produce different results:

\begin{itemize}

    \item Q11: returns \texttt{customer\_birth\_country} instead of \texttt{customer\_login}

After consultation with the professor, we have kept our optimisations that were built upon the incorrect queries. We believe we have still been able to demonstrate extensive understanding of benchmarking, identifying bottlenecks, query rewrites and execution plan tuning. Nevertheless, we strongly recommend future work to fix these queries before using our work as a new baseline.

\subsection{Query Optimisation Trade-offs Across Scale Factors}

The benefit of a query rewrite depends on how its additional work compares with the work it avoids as fact-table cardinalities grow. At a small scale factor, the fixed costs of materialising a common table expression, building a temporary result, or performing a second aggregation may be a substantial fraction of total execution time; at larger scale factors, avoiding repeated scans or oversized join intermediates can outweigh these costs. This pattern is consistent with the reported suite totals: the baseline grows by $37.2\times$ from SF1 to SF8, compared with $10.5\times$ for the optimised suite, and the reported improvement widens from $2.5\times$ to $8.8\times$. Group A's aggregate speedup likewise increases from $5.5\times$ to $29.8\times$. These figures indicate the potential scaling benefit of the rewrites, although the baseline and optimised suite runs were performed on different machines and should not be treated as a controlled, query-by-query causal comparison.

Materialising a selective date or dimension input and fixing the join order can protect a TPC-DS query from a cost-based plan choice that becomes poor as table cardinalities and optimizer estimates change. Query 21 illustrates this risk: the baseline takes about $0.30$\,s at SF1 but $53.31$\,s at SF2 after MySQL changes its access path, whereas the date-driven rewrite takes $0.10$\,s and $0.14$\,s, respectively. Such plan control is not free or universally preferable: materialisation adds temporary-table work, and \texttt{STRAIGHT\_JOIN} limits the optimizer's freedom to choose another order. Its value therefore depends on whether the driving input remains selective and whether the avoided scans or intermediate rows are large enough to justify the extra work; the example demonstrates a larger benefit at scale, not a measured low-scale regression.

Early aggregation and index-driven access have similarly scale- and data-dependent trade-offs. Grouping fact rows by compact surrogate keys can reduce the width and cardinality of data passed to later joins, but a grouping key that barely combines rows may not repay the grouping and subsequent re-aggregation costs: an initial Q47 approach reduced 1.34\,million rows to 0.96\,million and achieved only about a $1.5\times$ gain in a local SF2 test. Likewise, date-key index probes can be preferable to scanning an entire fact table when the qualifying range is selective: in Q21 at SF2, the nine qualifying weekly inventory snapshots covered only $3.4\%$ of inventory rows. If a predicate instead selects a large share of the fact table, repeated B-tree lookups can cost more than a scan. Consequently, scale factor alone does not determine the best plan; the degree of row reduction, intermediate cardinalities, access selectivity, and the optimizer's estimates should be evaluated together at each tested scale.

\section{Group A: Early Surrogate-Key Aggregation Before Dimension and Self-Joins (Law I + Law III)}

Queries in Group A (Q4, Q11, Q21, Q47, Q50, Q74, Q81) aggregate large fact tables (\texttt{store\_sales}, \texttt{catalog\_sales}, \texttt{web\_sales}, \texttt{catalog\_returns}, \texttt{inventory}) by string-valued dimension attributes (\texttt{customer}, \texttt{item}, \texttt{store}, \texttt{warehouse}), or self-join multi-year CTEs on string natural keys. By applying \textbf{Law I} (grouping fact rows by integer surrogate keys before joining dimensions) and \textbf{Law III} (driving from small, materialised \texttt{date\_dim} CTEs into fact-table indexes via \texttt{STRAIGHT\_JOIN}), we remove wide-string temporary tables, redundant self-joins and statistics-dependent plan choices.

\paragraph{Refinement of Law I.} Pushing the aggregation below the dimension join is only lossless when the outer grouping attributes are functionally determined by the surrogate key \emph{and} the query still groups by those attributes afterwards. In the TPC-DS data this cannot be taken for granted: \texttt{c\_customer\_id} is unique per \texttt{c\_customer\_sk}, but \texttt{item}, \texttt{store} and \texttt{warehouse} are slowly changing dimensions. At SF1, 18,000 item keys map to only 9,000 values of \texttt{i\_item\_id}, 12 stores share 8 store names and 5 warehouses share 4 names. Whenever a query groups by such attributes, our rewrites therefore aggregate by surrogate keys first and then \emph{re-aggregate} by the original attributes after the dimension join. This is exact for distributive aggregates: $\text{SUM}(\text{SUM}(x))$ equals $\text{SUM}(x)$, including returning \texttt{NULL} only when all inputs are \texttt{NULL}.

\paragraph{Baseline of Q4 and Q11.} The inherited \texttt{qmod\_combined} versions of Q4 and Q11 did not preserve the original queries: Q4 compared absolute 2001 totals instead of the 2001$\rightarrow$2002 growth ratios of the three channels, and both returned \texttt{customer\_birth\_country} instead of \texttt{customer\_login}. On SF1 the inherited Q4 returns 245 rows, whereas the original returns 8. Our optimised Q4 and Q11 implement the original semantics. Following the decision in Section~\ref{sec:important_notice}, the benchmark results below still compare them with the inherited baseline (marked with $^\dagger$). This understates their gain, because the original queries are considerably slower than the inherited ones: against the original queries, measured on our local instance, Q4 is $16.7\times$ (SF1) and $19.3\times$ (SF2) faster and Q11 $16.7\times$ and $17.3\times$.

\paragraph{Measurements and correctness.} All timings in the tables of this section come from the full benchmark (Section~\ref{sec:benchmark}): the historical baseline power test and the optimised suite measured as described in Section~\ref{sec:methodology}, at SF1, SF2, SF4 and SF8. As noted there, the two series were measured on different machines. The execution plans and the local measurements quoted in the text were obtained on a separate local instance (Apple M4, 10 cores, 24\,GiB RAM, MySQL 8.4.13, 6\,GiB InnoDB buffer pool) at SF1 (4.34\,GB including indexes) and SF2 (7.59\,GB). On this instance, correctness was verified by executing each optimised query and its baseline (the original query for Q4 and Q11) with the trailing \texttt{LIMIT} removed and comparing the complete result sets (exact comparison of decimals and strings, relative tolerance $10^{-9}$ for floating-point aggregates). All seven queries return identical results, in the same order, on SF1 and SF2.

\subsection{Group A Highlight: Query 21 Optimization}

\subsubsection{Baseline Execution Plan and Bottleneck Analysis}
Query 21 compares, per warehouse and item, the inventory on hand in the 30 days before and after 2002-03-20 for items priced between 0.99 and 1.49. In the full benchmark the baseline (\texttt{qmod\_combined/query21.sql}) takes only 0.30\,s on SF1 but 53.31\,s on SF2, a slowdown of about $180\times$ for twice the data, and 351.51\,s on SF8. \subsubsection{Precise Application of Optimization Laws in SQL}
We applied \textbf{Law III} and \textbf{Law I} to Query 21 as follows:
\begin{enumerate}
    \item \textbf{Application of Law III (Materialised Date Driving Order):} The 61-day window is materialised as a CTE and joined to \texttt{inventory} with \texttt{STRAIGHT\_JOIN}, which fixes the date-driven access path through the primary key prefix regardless of the index statistics. The price filter becomes a semi-join on a small materialised set of item keys.

    \textit{Before (Baseline):}
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
FROM inventory, warehouse, item, date_dim
WHERE i_current_price BETWEEN 0.99 AND 1.49
  AND i_item_sk = inv_item_sk
  AND inv_warehouse_sk = w_warehouse_sk
  AND inv_date_sk = d_date_sk
  AND d_date BETWEEN (CAST('2002-03-20' AS DATE) - INTERVAL 30 DAY)
                 AND (CAST('2002-03-20' AS DATE) + INTERVAL 30 DAY)
GROUP BY w_warehouse_name, i_item_id
\end{lstlisting}

    \textit{After (Law III Applied):}
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
WITH d_window AS (
    SELECT /*+ NO_MERGE() */ d_date_sk, d_date
    FROM date_dim
    WHERE d_date BETWEEN (CAST('2002-03-20' AS DATE) - INTERVAL 30 DAY)
                     AND (CAST('2002-03-20' AS DATE) + INTERVAL 30 DAY)
),
priced_items AS (
    SELECT /*+ NO_MERGE() */ i_item_sk, i_item_id
    FROM item WHERE i_current_price BETWEEN 0.99 AND 1.49
), ...
    FROM d_window d
    STRAIGHT_JOIN inventory inv ON inv.inv_date_sk = d.d_date_sk
    WHERE inv.inv_item_sk IN (SELECT i_item_sk FROM priced_items)
\end{lstlisting}

    \item \textbf{Application of Law I (Surrogate-Key Aggregation with Re-Aggregation):} The before/after sums are computed per integer key pair \texttt{(inv\_warehouse\_sk, inv\_item\_sk)}. Only then are \texttt{warehouse} and the item names joined, and because neither \texttt{w\_warehouse\_name} nor \texttt{i\_item\_id} is unique per key, the partial sums are aggregated again by these attributes before the ratio filter is applied.

    \textit{After (Law I Applied):}
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
inv_totals AS (
    SELECT /*+ NO_MERGE() */ inv.inv_warehouse_sk, inv.inv_item_sk,
           SUM(CASE WHEN CAST(d.d_date AS DATE) <  CAST('2002-03-20' AS DATE)
                    THEN inv.inv_quantity_on_hand ELSE 0 END) AS inv_before,
           SUM(CASE WHEN CAST(d.d_date AS DATE) >= CAST('2002-03-20' AS DATE)
                    THEN inv.inv_quantity_on_hand ELSE 0 END) AS inv_after
    ...
    GROUP BY inv.inv_warehouse_sk, inv.inv_item_sk
)
SELECT * FROM (
    SELECT w.w_warehouse_name, i.i_item_id,
           SUM(t.inv_before) AS inv_before, SUM(t.inv_after) AS inv_after
    FROM inv_totals t
    STRAIGHT_JOIN warehouse w ON w.w_warehouse_sk = t.inv_warehouse_sk
    STRAIGHT_JOIN priced_items i ON i.i_item_sk = t.inv_item_sk
    GROUP BY w.w_warehouse_name, i.i_item_id
) x
WHERE (CASE WHEN inv_before > 0 THEN inv_after / inv_before ELSE NULL END)
      BETWEEN 2.0 / 3.0 AND 3.0 / 2.0
\end{lstlisting}
\end{enumerate}

\subsection{Other Group A Queries}

\paragraph{Q4, Q11 and Q74: single-pass year pivot.} The baseline materialises a CTE that aggregates every sales channel by seven customer string columns and year (over all years for Q4 and Q11) and then self-joins it four times (six for Q4) on the string \texttt{customer\_id}. The rewrite scans each channel once, driven from the two target years of \texttt{date\_dim} through the sold-date foreign-key index (Law III), and groups by the integer customer key, computing both years with conditional aggregates such as \texttt{SUM(CASE WHEN d\_year = 2001 THEN ... END)} (Law I). The channels are then joined on \texttt{customer\_sk}, and \texttt{customer} is joined once for the output columns. Omitting the \texttt{ELSE} branch keeps a year whose values are all \texttt{NULL} at \texttt{NULL}, and a per-year \texttt{COUNT} preserves the requirement of the original self-joins that the customer has rows in both years. \texttt{STDDEV\_SAMP} in Q74 cannot be merged from partial results, but each (customer, year) group is still computed in a single aggregation. In the full benchmark Q74 is $5.5\times$ (SF1) to $12.3\times$ (SF8) faster; for Q4 and Q11, see the note on their baseline at the beginning of this section.

\paragraph{Q47: integer group identifiers and window functions.} A first attempt that pre-aggregated \texttt{store\_sales} by \texttt{(ss\_item\_sk, ss\_store\_sk, month)} gained only about $1.5\times$ on our local SF2 instance: this key barely reduced the rows (1.34M to 0.96M), and the second aggregation by the string attributes added another full pass. Law I only pays off when the surrogate-key grouping is clearly coarser than the original grouping. The final version maps \texttt{(i\_category, i\_brand)} and \texttt{(s\_store\_name, s\_company\_name)} to integer group identifiers with \texttt{DENSE\_RANK} (which, like \texttt{GROUP BY}, compares strings by collation), aggregates \texttt{store\_sales} once by these integers directly into 76k groups, and replaces the three-way self-join for the previous and next month with \texttt{LAG}/\texttt{LEAD}. Since the original self-join uses equality predicates that never match \texttt{NULL}, partitions with a \texttt{NULL} category, brand, store or company name are excluded in the rewrite as well. In the full benchmark it is $4.6\times$ to $5.2\times$ faster up to SF4 and $40.7\times$ at SF8, where the baseline degrades from 23.08\,s (SF4) to 421.75\,s.

\paragraph{Q50: fixed return-driven plan.} In the baseline Q50 takes at most 0.15\,s up to SF4 but 75.81\,s at SF8. The rewrite fixes the access path from the 31 days of August 2001 into \texttt{store\_returns} through its returned-date index and into \texttt{store\_sales} through its primary key \texttt{(ss\_item\_sk, ss\_ticket\_number)}, counts the return intervals per \texttt{ss\_store\_sk} and only then re-aggregates by the ten store attributes. The full benchmark confirms the benefit at SF8: the optimised query grows smoothly to 0.09\,s, $825.4\times$ faster than the baseline.

\paragraph{Q81: decorrelated per-state threshold.} The baseline evaluates the average return per state as a dependent subquery, rescanning the matching CTE rows for every outer row, so its cost grows roughly quadratically with the data (17.72\,s on SF4, 507.15\,s on SF8). The rewrite materialises the per-customer returns once, driven from the 2002 dates through the \texttt{catalog\_returns} returned-date index, pre-aggregates the threshold $1.2 \times \text{AVG}$ per state (Law I) and joins it on the state. A \texttt{NULL} state matches neither the original predicate nor the join. The outer filter on \texttt{ca\_state = 'NH'} cannot be pushed into the CTE, because it refers to the customer's current address and not to the address of the return. In the full benchmark the speedup grows from $16.3\times$ at SF1 to $707.3\times$ at SF8 (0.72\,s).

\subsubsection{Precise Application of Optimization Laws in SQL}
We applied **Law I** and **Law III** to Query 72 as follows:
\begin{enumerate}
    \item \textbf{Application of Law I (Distributive Pre-Aggregation of \texttt{catalog\_sales}):} Any two \texttt{catalog\_sales} rows in the same week that share $(\texttt{cs\_item\_sk}, \texttt{d\_week\_seq}, \texttt{cs\_quantity})$ match the exact same set of \texttt{inventory} records under $(\texttt{cs\_item\_sk} = \texttt{inv\_item\_sk} \land \texttt{d1.d\_week\_seq} = \texttt{d2.d\_week\_seq} \land \texttt{inv\_quantity\_on\_hand} < \texttt{cs\_quantity})$. Pre-grouping \texttt{filtered\_cs} by these three integer columns collapses duplicate item-week-quantity sales before probing \texttt{inventory}, and delays joining the wide \texttt{item} (\texttt{VARCHAR(200)}) and \texttt{warehouse} strings until after the fact join.

    \textit{Before (Baseline):}
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
SELECT i_item_desc, w_warehouse_name, d1.d_week_seq,
       SUM(CASE WHEN p_promo_sk IS NULL THEN 1 ELSE 0 END) no_promo,
       SUM(CASE WHEN p_promo_sk IS NOT NULL THEN 1 ELSE 0 END) promo,
       COUNT(*) total_cnt
FROM catalog_sales
JOIN inventory ON (cs_item_sk = inv_item_sk AND inv_quantity_on_hand < cs_quantity)
JOIN warehouse ON (w_warehouse_sk = inv_warehouse_sk)
JOIN item ON (i_item_sk = cs_item_sk)
...
LEFT OUTER JOIN promotion ON (cs_promo_sk = p_promo_sk)
\end{lstlisting}

    \textit{After (Law I Applied):}
\begin{lstlisting}[language=SQL, basicstyle=\ttfamily\scriptsize, breaklines=true, frame=single]
filtered_cs AS (

           SUM(CASE WHEN p.p_promo_sk IS NULL THEN 1 ELSE 0 END) AS no_promo_cnt,
           SUM(CASE WHEN p.p_promo_sk IS NOT NULL THEN 1 ELSE 0 END) AS promo_cnt,
           COUNT(*) AS cs_cnt

    STRAIGHT_JOIN date_dim d3 ON cs.cs_ship_date_sk = d3.d_date_sk AND d3.d_date > d1.d_date + 5

)
\end{lstlisting}

\section{Group C: Disjunctive Predicate Pushdown and Star-Join Ordering (Law II + Law III)}

Group C contains Queries 13, 46, 48, 63, 73, and 79. These are the six rewrites that reduced execution time on SF1 in our measurements. Their common challenge is that selective conditions are either coupled across several branches of an \texttt{OR} predicate or applied in a multi-table join where join order affects how much of a fact table is read. We apply the selection-pushdown rule (Law II) and the join-order rule (Law III), introduced in the optimization framework above, to expose safe filters and guide the plan toward selective inputs.

\subsection{Law II: Selection Pushdown and Disjunctive Bounding-Box Extraction}

Law II moves a predicate to the relation that owns the filtered attribute, so rows outside the needed domain are removed before a large join. When an \texttt{OR} combines predicates from multiple relations, each relation can first be restricted to the union of values that occur in the branches. These independent filters are only bounding boxes: they may admit cross-branch combinations that were not valid in the original query. The original branch-by-branch predicates must therefore remain as residual conditions after joining. For Query 13, the household, demographic, and address candidates are filtered in advance, and the fact rows receive broad price and profit bounds while the exact correlations are preserved.

\subsection{Law III: Join Associativity and Deliberate Physical Join Order}

Inner joins can be associated in different orders without changing their relational result, but each order can produce different intermediate cardinalities and access paths. Law III materializes useful filtered inputs with \texttt{NO\_MERGE()} and uses \texttt{STRAIGHT\_JOIN} where needed to drive from a selective date or dimension input into a fact-table index. These are plan-shaping techniques rather than performance guarantees; the resulting execution tree must be checked for each workload and scale factor.
